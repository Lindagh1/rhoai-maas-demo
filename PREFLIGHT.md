## Interpretation

**SAFE TO CONTINUE: YES.** The cluster itself is healthy (no CrashLoopBackOff, no
OOMKilled, 10%/23% node utilization). Nothing here is a genuine health blocker —
every `MISSING` line is an expected, not-yet-installed MaaS prerequisite on a
brand-new sandbox. This matches the documented state before following
[Deploy and manage Models-as-a-Service](https://docs.redhat.com/en/documentation/red_hat_openshift_ai_self-managed/3.5/html/govern_llm_access_with_models-as-a-service/deploy-and-manage-models-as-a-service).

## Schema verification (Phase 1)

Confirmed directly against the live cluster with `oc explain` (not assumed from
older docs):

- `spec.components.kserve.modelsAsService.managementState` **exists** in the
  installed `DataScienceCluster` v2 CRD and is the correct, current field for
  RHOAI 3.5 (verified against the official 3.5 docs, section 1.6 "MaaS
  configuration"). Currently `Removed`.
- A **separate, unrelated** field `spec.components.aigateway.modelsAsAService`
  (note: "AsAService", not "AsService") also exists in this CRD version. This
  is a distinct, newer "AI Gateway" modularization path referenced by some
  community examples but **not** the mechanism documented in the official
  RHOAI 3.5 "Govern LLM access with Models-as-a-Service" guide. Per explicit
  instruction, this demo uses **only** `kserve.modelsAsService`, matching the
  official docs and its "gateway-scoped `AuthPolicy`" architecture
  (single `maas-gateway-auth` per tenant gateway, replacing the old per-model
  pattern).
- `spec.components.ogx.managementState` exists and must be `Managed` to expose
  MaaS user-facing features (Gen AI Studio) per official docs section 1.7.
- `OdhDashboardConfig.spec.dashboardConfig.{modelAsService,genAiStudio,
  maasAuthPolicies,vLLMDeploymentOnMaaS}` all exist on the live
  `odh-dashboard-config` object. `modelAsService` and `genAiStudio` are
  **already `true`** on this sandbox (pre-set, harmless — dashboard flags do
  not enable MaaS by themselves, `kserve.modelsAsService.managementState`
  does). `maasAuthPolicies` is unset and will be added. `vLLMDeploymentOnMaaS`
  is unset and will **stay unset** (Technology Preview, out of scope).

## Additional platform facts discovered

- Cluster platform: **AWS** (cloud) → no MetalLB required; the Gateway gets a
  real ELB address automatically.
- `authorino-operator` (v1.4.2) is **already installed** cluster-wide (as a
  dependency pulled in for KServe's existing authenticated-inference support)
  but **no `Authorino` custom resource instance exists yet** — Kuadrant needs
  to be installed first, since the Kuadrant operator is what actually creates
  the `Authorino` CR when it reconciles the `Kuadrant` resource.
- `rhcl-operator` (Red Hat Connectivity Link) v1.4.2 is available in the
  `redhat-operators` catalog — matches the documented "1.4.x" requirement
  exactly.
- Two GatewayClasses already exist and are `Accepted=True`
  (`data-science-gateway-class`, `openshift-ai-inference`), both using
  controller `openshift.io/gateway-controller/v1`. No `openshift-default`
  GatewayClass exists. Per docs: "you have created a GatewayClass ... **or**
  you are using the pre-existing `openshift-default` GatewayClass" — since
  neither of the existing GatewayClasses is named `openshift-default` and
  reusing an existing one is a shared/owned resource of unclear intent, this
  demo creates its own dedicated `openshift-default` GatewayClass (as named in
  the official companion guide) rather than repurposing someone else's
  GatewayClass. This does not modify or delete any existing GatewayClass.
- Two Gateways already exist in `openshift-ingress`
  (`data-science-gateway` — owned by RHOAI's dashboard `GatewayConfig`;
  `openshift-ai-inference` — serves the pre-existing `my-first-model`
  namespace). **Neither is touched.** A new, separate `maas-default-gateway`
  is created per the official docs.
- LWS (Leader Worker Set) operator is **not installed**. It is used by llm-d
  for multi-node distributed inference. This demo deploys a single-replica
  (`replicas: 1`) CPU simulator via `LLMInferenceService` in RawDeployment
  mode (the DSC's `kserve` component description confirms "Only RawDeployment
  mode is supported" on this cluster), which does not require LWS. LWS is
  intentionally **not installed** to keep the changeset minimal and avoid
  unrelated operators, per the safety rules.
